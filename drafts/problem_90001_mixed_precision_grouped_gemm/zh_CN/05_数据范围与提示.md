## 数据范围

* `A` dtype 为 `torch.float8_e4m3fn`
* `A_scale`、`B_scale` dtype 为 `torch.float32`
* `B_packed` dtype 为 `torch.uint8`
* `m_indices` dtype 为 `torch.int32`
* `D` dtype 为 `torch.bfloat16`
* `group_k` 固定为 64
* `M_total <= 32768`
* `K <= 4096`
* `N <= 4096`
* `num_groups <= 128`
* `m_indices` 可能包含 padding 行、空 group、极端热门 group 和大量小 group

## Group 分布

评测会覆盖多种 group 分布：

* `balanced`：每个 group 的有效 token 数接近
* `long_tail`：少数热门 group 占大部分 token
* `many_small`：大量 group 只有很少 token，少数 group 较大
* `sparse_groups`：部分 group 完全为空

padding 行比例可能在 `0%` 到 `40%` 之间。`m_indices[i] == -1` 的行必须输出 0。

`A_scale` 和 `B_scale` 可能包含 0，也可能几乎不包含 0。scale 为 0 时对应分块的真实值为 0，但评测不会保证所有测试点都能从 zero-scale skip 中获得收益。

## 优化提示

提交编辑器中给出的初始 CUDA 代码是朴素 baseline，正确但较慢。你可以基于它优化，也可以完全重写。

* 不要先把完整 `B` 反量化到全局内存。
* 同一 group 的多行 token 可以复用对应的 `B_packed` 和 `B_scale`。
* INT4 unpack、scale 读取和矩阵乘应尽量融合。
* padding 行需要快速跳过或清零。
* 评测会覆盖不同 `M_total/N/K/num_groups`、不同 group 分布、不同 padding 比例、不同 scale 稀疏度，以及不总是适合固定 tile 的边界尺寸。
* 部分测试点的 `K` 是 128 的倍数，适合高性能 fast path；部分测试点的 `K` 不是 128 的倍数，用于检查边界处理和 fallback 性能。

## 约束

* 不允许修改只读输入 tensor。
* 不建议在 `run_kernel` 内部调用 `cudaDeviceSynchronize()` 或其他显式同步。
* 不允许依赖固定测试点写死输出或只针对单一尺寸、单一 padding 比例、单一 scale 稀疏度做特化。
* 不允许使用 CPU 参与计算。
* 比赛组织方可限制 cuBLAS、cuDNN、CUTLASS、`cudaMalloc`、`cudaFree` 等库调用或动态分配行为。

## 评分目标

所有测试点必须先通过正确性检查。正确通过后，成绩按照运行时间或相对官方参考实现的加速比计算。测试点均为正式排名测试点，覆盖不同规模、不同 group 分布和不同边界形状。

## 测试点设计

正式评测建议使用 7 到 8 个有区分度的大规模测试点，而不是大量小测试点。推荐覆盖：

* 热门 group 占主导的 `long_tail` case
* 深 K、小 N 的 `many_small` case
* 大 N、稀疏 group 的 `sparse_groups` case
* 大规模 `balanced` case
* `K/N` 不整除常见 tile 大小的边界 case
* 高 padding 比例 case
* 极深 K case
* 低 padding 或无 padding case
* scale 几乎不含 0 的高算力密度 case
* `K` 不是 128 倍数的 fallback case
